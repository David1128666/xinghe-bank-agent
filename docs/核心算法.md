# 核心算法说明

文档基准：2026-10-29。本文所称“算法”为仓库内已实现的确定性规则与状态转换，不包含机器学习训练、推理模型、真实反欺诈服务或投资预测。

## 1. 主处理流程

输入经规则解析得到结构化请求，再由核心 Agent 执行下列流程。网页额外提供首次身份与小额直接转账策略；命令行仍使用核心默认的显式确认流程。

```text
中文输入或表单生成的指令
  → 规则识别操作、提取金额/日期/对象/用途
  → OperationRequest
  → 配置、工具、敏感字段与必填字段检查
  → 认证
  → 收款对象解析（网页首次对象先身份核对）
  → 合并操作风险下限与模拟风险
  → 查询并返回，或创建操作预览
  → 显式确认 / 网页小额策略 / 已确认范围授权
  → 写执行前审计 → 使用幂等键执行一次
  → 按同一键查询结果 → 如实显示任务状态
```

对应代码：[agent.py](../banking_agent/agent.py) 的 `submit`、`_prepare_account_operation`、`_resolve_and_assess`、`_assess_and_continue`、`_create_preview`、`confirm` 与 `_execute_once`。

## 2. 中文意图解析与字段补齐

### 2.1 规则识别

[DemoConversation._parse](../banking_agent/demo.py) 依顺序检查关键词、正则表达式和内置代码。例如“转账/转给/汇给”进入转账解析，“账单/消费分析”进入账单查询，`XH001` 等虚构代码结合买入指令进入股票操作。字段提取包括：

- 金额：`_extract_amount` 从“数字＋元/块/人民币/CNY”提取最多两位小数；负金额触发错误。结构化检查随后再次验证数值与正值条件。
- 日期：`_extract_dates` 解析受支持的日期表达；账单可使用月份、年份或起止日期。
- 用途、备注、原因：`_extract_named_value` 按指定标签提取。
- 操作对象：产品、卡片、订阅、计划使用内置代码、尾号或规则字段；转账对象采用专门解析。

规则分支有优先顺序，不会同时理解任意多个意图。多步骤应使用“组合计划：步骤一；步骤二”进入显式工作流，而不是假定自由文本会自动生成可靠计划。

### 2.2 网页默认值与缺失信息

[BrowserDemoConversation._parse](../banking_agent/web_app.py) 为短句设置可见的演示默认值：未明确指定账户时使用活期账户，未表达预约/未来时间时使用 `now`，空用途使用“日常转账”。明确但无法识别的账户、尾号或未来时间不会静默变为立即付款。

`BankingAgent._missing_information` 对结构化请求检查必填字段，缺失则进入 `AWAITING_INFORMATION`。后续 `_supplement` 仅补充当前任务需要的信息，`provide_information` 合并到原请求后从必填字段和认证阶段重新校验，保留原金额和任务身份。

例如：“转账2888元”缺收款人，随后输入“张三”会补齐原任务，不会把 2888 元丢失后创建另一笔默认转账。

**限制：**规则不具备通用语义理解；不支持的别名、错别字、中文大写金额、复杂否定句或多义句可能要求补充信息。姓名黑名单还可能拒绝包含“和/或/与/及”等字的正常姓名。应按展示的字段和预览核对，不能将解析器描述为高准确率自然语言模型。

## 3. 收款人解析与首次身份核对

### 3.1 完整姓名优先

网页的 `explicit_recipient_name` 先移除“用途/备注/原因”之后的文本，再从“给/向/为/转给/汇给”等前缀及金额、转账动词、周期词等边界提取姓名。`valid_recipient_name` 限定 2 至 16 个中文字符或中点，并拒绝代词、泛指对象、操作词和多对象连接词。

网页不把“张小明”按姓名子串识别成“小明”，也不把“用途给小明买早餐”当成收款人。基础 `SimulatedBank.resolve` 优先完整姓名匹配；多个同名对象仍要求选择尾号。若没有完整姓名匹配，模拟工具还支持演示手机号或历史备注搜索，这不是生产级账户识别。

### 3.2 首次身份状态

`BrowserDemoAgent._resolve_and_assess` 在转账对象未核对时，将原任务暂停为：

```text
state = AWAITING_INFORMATION
error_code = recipient_identity_required
missing_information = [recipient_identity]
```

`BrowserSession.stage_recipient_identity` 创建待核对对象与随机 token；新姓名默认四位尾号为 `1000 + int(SHA256(name)[:8], 16) % 9000`。这是让同一虚构姓名有稳定演示尾号的规则，**不查询、不推算真实银行账户**；用户可在弹窗修改。

确认时 `handle_recipient_identity` 依次验证：当前 token、会话 revision、原任务状态、姓名格式和四位尾号。若编辑为已有姓名，尾号必须对应该姓名的现有演示记录，避免把已有联系人误改为另一个账户。然后先写身份确认审计，再保存 `known=True` 的合成联系人，通过原任务 `provide_information` 继续认证、风险和付款流程。

取消核对不保存、不扣款。确认后若付款失败，已保存联系人可能保留。列表仅在本轮浏览器会话内保存，不是永久通讯录；刷新保留，新一轮演示或重启清空。

对应代码：[web_app.py](../banking_agent/web_app.py) 的 `valid_recipient_name`、`explicit_recipient_name`、`BrowserDemoConversation`、`stage_recipient_identity`、`handle_recipient_identity`；测试：[test_recipients.py](../tests/test_recipients.py)。

## 4. 认证、风险合并与预览复验

### 4.1 风险采用“只升不降”的合并规则

[policy.effective_risk](../banking_agent/policy.py) 的核心规则：

```text
effective_level = max(minimum_risk(operation), tool_assessment.level)
若工具要求人工审核：effective_level = R4
转账达到高额或单笔达到日限额：effective_level = R4
```

操作的最低等级由 `minimum_risk` 决定：公共资料 R0，普通账户查询 R1，预算/提醒/临时锁卡等 R2，转账和多数变更至少 R3。因此金额小并不意味着核心风险等级降到 R1；网页 3000 元边界是单独的授权策略。

模拟工具 `SimulatedBank.assess` 使用固定关键词检测诈骗、胁迫、异常设备等情况；未核对收款人、适当性不匹配、累计限额等也可升为 R4。演示配置包含低额阈值 1000、高额阈值 10000、日累计阈值 20000 CNY，阈值不是安全性验证结论。

累计值由 `_daily_transfer_total` 按上海日期汇总当前虚构用户全部账户，包含即时转账、AA 实际付款和手动模拟执行的定时转账。`amount >= high` 或 `today_total + amount >= daily` 会要求审核，恰好到达边界也会升级。

### 4.2 认证与确认摘要

非公共查询一般需要 `STANDARD`，变更需要 `ENHANCED`；敏感查询可升级。模拟渠道 `app/im/other` 分别返回增强/标准/无认证等级，不能视为真实登录或多因子认证。具体分级见权限文档。

`_create_preview` 为变更生成可信工具预览、随机幂等键、确认短语、有效期和摘要。`_preview_digest` 对公开预览及风险的等级/标志/审核要求/规则编号规范化后计算 SHA-256。默认确认有效期为 300 秒。

`confirm` 重新检查任务归属、状态、渠道、有效期和确认短语，并重新认证、评估风险、生成预览。若摘要变化，更新摘要并要求再次确认；R4 在确认后提交模拟审核，不能调用执行工具。渠道切换使旧确认失效。

## 5. 网页小额即时转账策略

只有 [BrowserDemoAgent._direct_transfer_authorized](../banking_agent/web_app.py) 启用此策略；基础 `BankingAgent` 同名钩子恒为 `False`，命令行仍走确认。

直接转账需同时满足：

1. 操作为 `TRANSFER`；有效金额与预览金额一致，且 `0 < amount < 3000`，小数位不超过两位。
2. 请求和预览均为 CNY，预览费用为 0。
3. 执行时间为 `now`，频率为 `once`；已解析出收款对象。
4. 风险不为 R4，且无需人工审核。
5. `_try_direct_transfer` 再次认证、评估风险和生成预览，摘要没有改变且仍满足上述条件。

```text
新收款人 + 2888：首次身份核对 → 普通检查通过 → 直接付款
已核对收款人 + 25：普通检查通过 → 直接付款
任意收款人 + 3000：必要时先核对身份 → 转账摘要 → 确认后办理
小额 + 诈骗信号 / 累计风险：不能使用小额策略绕过审核
小额 + 定时/周期：不能使用小额策略跳过摘要确认
```

使用策略时审计事件为 `configured_transfer_authorization_used`，明确记录 `required=False, received=False`，不虚构“用户点击了确认”。报价/风险变化则退回确认。测试：[test_web.py](../tests/test_web.py)。

## 6. 虚构股票的报价、费用与持仓

[SyntheticStockMarket](../banking_agent/stocks.py) 仅支持 XH001、XH002、XH003，固定样例价格分别为 12.80、26.50、8.60 元。股数必须为 100 的正整数倍，最多 100 万股；仅使用演示活期账户。

全部金额计算使用 `Decimal`，费用按分 `ROUND_HALF_UP`：

```text
principal = price × shares
fee       = round_half_up(principal × 0.001, 0.01)
total     = principal + fee

new_shares     = old_shares + shares
new_cost_basis = old_cost_basis + total
average_cost   = new_cost_basis / new_shares（展示时保留两位小数）
market_value   = fixed_sample_price × held_shares
unrealized_pnl = market_value - cost_basis
```

例如 XH001 的 100 股本金为 1280.00 元、费用 1.28 元，总扣款 1281.28 元。固定价格下，初次样例浮动盈亏为 -1.28 元，即手续费影响，不是市场价格预测。

点击“买入”发出明确的 `buy_stock` 请求，核心生成服务端预览并要求用户确认；2026-11-01 加固版起 `is_pre_authorized()` 只对 `CROSS_SCENARIO` 的范围授权生效，投资类操作不再有免确认路径。执行仍检查可用余额、预留预算与报价一致性，并保留认证、审计与幂等检查。

金额在入口统一按分量化（`BankingAgent._normalize_amounts`）后回写 payload，因此预览金额与最终扣款金额一致；文本解析对科学计数法、千分位、全角数字和三位以上小数直接拒绝，不做截取。

测试：[test_stocks.py](../tests/test_stocks.py)。没有实时行情、卖出撮合、交易所清算或真实证券适当性服务。

## 7. 账单汇总与启发式分析

[SimulatedBank._bill_report](../banking_agent/demo.py) 先按选定日期区间过滤交易，再对分类、商户和月份做 `Decimal` 求和。日期区间、年份、月份由 `_resolve_period` 校验；自定义区间最长 3660 天。

`_recurring_detections` 将商户名的固定虚构后缀标准化，同一商户至少出现两笔且覆盖至少两个不同月份时，标记为“疑似周期性支出”。它没有核验固定扣款日、金额相似度或商户合同，因此不保证是订阅。

异常展示直接读取合成交易已有的 `anomaly_features` 标签；没有训练异常检测模型。节省建议查看支出最高的前两类，类别金额超过 100 元时提示回看；发现周期支出再提示检查是否仍在使用。建议不自动取消服务或提交争议。

理财匹配 `_assess_product_fit` 按虚构地区、风险承受、期限、金额、流动性、目标、经验和限制逐项筛选；资料不全只展示目录，不生成个性化匹配。期限按年/月/天转换，属于演示规则筛选，没有预期收益优化。

## 8. 预算预留与计划范围授权

可用余额为账面余额减去账户已预留金额；创建未来开始的预算计划不会立刻预留，须显式模拟激活。预算预留影响后续转账及股票等余额检查。

`_within_purchase_scope` 对待采购订单逐项检查正金额、商品集合、商户白名单，并汇总重复商品行，随后同时检查：

- 计划处于可执行状态，已到采购日或显式模拟到期。
- 本次总额不超过单次上限、剩余预留及账户预留。
- 累计总支出不超过商品预算合计，各单一商品累计不超过该商品预算。
- 次数未达到上限，当前日期未超过有效期。

`range/continuous` 授权只有在上述范围内才可能直接执行；新诈骗信号仍可升级 R4，阻止自动执行。`once` 采购需要显式确认。多商品逐笔记录与审计，部分成功时不自动重试已完成订单，未使用预留可按取消流程释放。

该算法核验的是合成订单字段，不证明真实商户、商品、配送或家庭关系。组合商品总价缺少真实逐项商品发票和外部核验，范围授权不能替代真实采购控制。

## 9. 多步骤依赖编排

[BankingWorkflow](../banking_agent/workflow.py) 将输入请求构造成线性依赖链：`step-i` 依赖 `step-(i-1)`。`advance` 按顺序扫描，只有依赖状态为 `SUCCESS` 才提交下一步。每步重新调用同一个 Agent，不越过单项认证、确认或风险策略。

待认证、待确认、审核、处理中、定时或未知状态会暂停后续步骤；失败、取消或部分成功会把未开始步骤标为 `NOT_EXECUTED`。取消只停止未开始/可取消步骤，不自动撤销已完成转账或已登记定时任务。

这是显式顺序工作流，没有任意 DAG 调度、并行任务规划、补偿事务或后台重试器。

## 10. 多层幂等与审计算法

| 层次 | 键与校验 | 结果 |
| --- | --- | --- |
| 浏览器 | `request_id → 规范化完整请求指纹` | 同号同内容返回当前状态；同号不同内容拒绝；新请求需当前 `revision` |
| 核心 | `(user_id, session_id, request_id) → 请求指纹和任务` | 对提供了 request_id 的核心请求复用任务；同号冲突失败 |
| 执行 | `idempotency_key → ExecutionResult` | 模拟执行工具复用已记录结果；核心先置 `PROCESSING`，再提交与查询 |

执行超时或抛错后可能已经产生副作用，核心不会自动重提，而是 `lookup` 原幂等键；查不到结果标记 `UNKNOWN`，刷新也只查原键。上述映射都在内存中，不提供重启恢复、跨进程去重或数据库级原子性。

[AuditLog](../banking_agent/audit.py) 对规范化 JSON 计算：

```text
entry.prev_hash = previous_event_hash
entry.event_hash = SHA256(canonical_json(entry_without_event_hash))
```

用户/会话标识另用 HMAC-SHA256 散列。追加时采用进程内锁、追加写和 `fsync`，启动时逐条验证哈希链。执行前审计失败会阻止跨越付款边界；提交后审计失败或查不到状态，不能简单宣称交易失败且没有扣款。

日志链是“可发现未同步重算的修改”，不是加密、数字签名、外部锚定或不可变存储。拥有文件和代码权限的人可删除/重写整条链，演示标识密钥也是公开固定值。

## 11. 复杂度与适用范围

以下以输入长度 `L`、规则数 `K`、收款人数 `R`、交易数 `N`、分类数 `C`、月份数 `M`、步骤数 `W`、持仓代码数 `P`、审计记录数 `A` 表示。为当前有限规则的工程估计，不是正则最坏情况证明。

| 算法 | 主要时间开销 | 主要空间开销 |
| --- | --- | --- |
| 规则解析 | 多个关键词/正则扫描约 `O(KL)`；姓名后备扫描约 `O(RL)`，名称排序 `O(R log R)` | 请求字段与当前输入；排序约 `O(R)` |
| 精确姓名、电话/备注解析 | 当前字典全扫描 `O(R)` | 匹配/候选列表 `O(R)` |
| 账单汇总与周期支出 | 过滤分组 `O(N)`，分类排序 `O(C log C)`，月份排序 `O(M log M)` | 返回明细与分组约 `O(N+C+M)` |
| 股票报价/成交 | 固定目录字典查找及单持仓更新平均 `O(1)`；全部持仓展示 `O(P)` | 订单随成交次数增长，持仓 `O(P)` |
| 工作流 | 单次扫描约 `O(W)`；每次只推进少量步骤时重复调用累计可达 `O(W²)` | `O(W)` 加单项任务 |
| 审计验证/追加 | 验证 `O(A)`；追加还受磁盘同步延迟影响 | 验证逐行读取；文件随事件数增长 |
| 去重 | 内存字典平均 `O(1)` 查找，指纹序列化取决于请求长度 | 随任务/请求数增长；当前不淘汰 |

当前设计面向单机课堂演示和有限样例数据，未进行高并发、长时间运行、真实数据准确率或生产安全认证。可执行验证入口见 [tests/](../tests/) 和仓库测试说明。
